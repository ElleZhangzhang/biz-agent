一、项目一句话介绍

D:\reactLearning\biz-agent —— 面试作品：Agent 通过 LLM function calling 操作一个模拟电商业务系统，带人工审批（HITL）挂起恢复和 SSE 流式事件推送。前端 React 19 + Vite 8 + antd 6 + zustand（已装未用），后端 Express 5 + TS（tsx 运行），LLM 走 OpenAI 兼容协议（DeepSeek）。

三、后端 —— 全部完成并 E2E 验证 ✅

- server/src/business/types.ts：Product、OrderStatus、RiskLevel、OrderItem、Order（含 note?）。
- server/src/business/system.ts：内存数据（seed 商品 p1~p8，orders 数组）。overview() / listOrders(status?) / getOrder(id) / createOrder / updateOrderStatus（NEXT_STATUS 状态机：pending→processing/cancelled→shipped→completed；cancel 退还库存；riskLevel = 金额≥5000 high / ≥1000 medium / 其余 low）。业务变更统一返回 { ok: true, ... } | { ok: false, error }。
- server/src/agent/tools.ts：Tool 接口（含 requiresApproval?: boolean）+ 3 个工具：get_overview / get_order / cancel_order（requiresApproval: true）。
- server/src/agent/approvals.ts：审批中枢。createApproval / getApproval / listApprovals / decideApproval(id, decision) / waitForApproval(id)。核心机制：waiters = Map<string, resolve>，跨 HTTP 请求共享模块内存，事件驱动唤醒（非轮询）。ApprovalDecision = 'approved' | 'rejected'，ApprovalStatus = 'pending' | ApprovalDecision。
- server/src/agent/agentLoop.ts：runAgent(prompt, decide, onEvent)。Decide 接口 (messages) => Promise<Step>，Step = {content} | {toolCalls}，MAX_TURNS=5。闸门：requiresApproval → createApproval → onEvent(approval_required) → await waitForApproval(id) → approved 才 tool.execute(args)，rejected 返回 { rejected: true, message }（纵深防御：安全由系统闸门保证，不靠 LLM 自觉，SYSTEM_PROMPT 已改写）。
- server/src/agent/mockAgent.ts / llmAgent.ts：Decide 的两种实现，process.env.LLM_API_KEY 存在时用真 LLM。
- server/src/routes/agent.ts：POST /api/agent/run（body { prompt }）。SSE 三件套 + flushHeaders，每帧 data: {json}\n\n，事件 type：tool_call（name, arguments 是 JSON 字符串）/ tool_result（name, result）/ approval_required（approvalId, toolName, args）/ done（content，推完关连接）/ error。
- server/src/routes/approvals.ts：GET /api/approvals 列表、POST /api/approvals/:id/decide（body { decision: 'approved' | 'rejected' }，运行时校验）。
- server/src/routes/business.ts：GET /overview、GET /orders?status=、GET /orders/:id、POST /orders、PATCH /orders/:id/status。
- server/src/index.ts：3001 端口，import 'dotenv/config' 第一行，/api/health。

六、运行方式

- 两个终端：cd server && pnpm dev（3001）；cd client && pnpm dev（5173，/api 代理到 3001）
- 造订单：curl -X POST http://localhost:3001/api/business/orders -H "Content-Type: application/json" -d '{"customerName":"张三","items":[{"productId":"p1","qty":2}]}'
- HITL E2E 复测配方：创建订单 → 控制台发"取消订单 o1" → 见 approval_required 挂起 → decide approved → 流恢复 → 订单 cancelled + 库存退还

七、技术注意点

- client tsconfig 有 verbatimModuleSyntax（类型必须 import type 或内联 type）、noUnusedLocals、无 strict；@/* → ./src/*
- 已知后端不一致（面试可讲）：GET /orders/:id 返回 {ok, order}，其余读接口都是 {ok, data}——前端要做订单详情格时统一
- 可选后续：mockAgent 的 get_order 参数提取（正则 /o\d+/）让无 key 也能跑、mock RULES 加 cancel_order、token 级流式、消息列表自动滚动到底部、zustand 等跨组件共享需求出现时再用

补充：① 操作环境的坑（Windows + Git Bash，来自历史会话踩过的雷）

- Git Bash 粘贴 curl 命令会带入隐形字符导致 400/解析失败 → 用 -d '{"a":1}' 单引号整段或手动重敲
- Windows 下 tsx -e 多行命令会吞输出 → 写成单行
- 后台跑 server 的任务退出码不可信 → 杀进程用端口：netstat -ano | findstr 3001 + taskkill /PID
- server 重启后订单内存数据清空（详见 ⑤）

② 环境变量配置项（只写名字，不碰值）

server/.env 里有：LLM_API_KEY、LLM_BASE_URL（默认 https://api.deepseek.com）、LLM_MODEL（默认 deepseek-chat）。
routes/agent.ts 的 decide 选择逻辑：LLM_API_KEY 存在 → createLLMDecide（真 LLM）；否则 → createMockDecide。
铁律：任何情况下不打印/读取/引用 LLM_API_KEY 的值。

③ 两个已知设计边界（面试要能答上来）

- waitForApproval 没有超时：没人审批，SSE 连接永远挂着（这是 HITL"暂停"特性，也是限制）
- 订单/商品全在内存：server 重启即清空（demo 项目可接受，可答"换 Redis/DB 的升级路径"）
- 另外 Grid 4 做按钮时注意：审批完成后要防止按钮重复点击（POST 两次 decide 会收到 400"该审批单已处理"）
